# `security` — справочник акций

**Назначение:**
Справочник акций, входящих в scope проекта. Содержит идентификационные и справочные характеристики ценных бумаг, а также внешний идентификатор T-Invest, необходимый для получения дивидендных данных.

**Источники:**
Основной источник справочных данных — MOEX ISS.

Endpoint:

`https://iss.moex.com/iss/engines/stock/markets/shares/boards/TQBR/securities.json`

Используемый блок ответа: `securities`.

Дополнительный источник — T-Invest API.

T-Invest используется только для получения `tbank_uid`, необходимого для последующей загрузки дивидендных событий.

**Scope:**
В таблицу загружаются только акции, указанные в `config/scope.toml`.

Список инструментов может расширяться. При добавлении нового `SECID` в конфигурацию соответствующая запись должна быть получена из MOEX ISS и добавлена в справочник.

**Зерно:**
Одна строка = одна акция.

**Business key:**
`SECID` — код ценной бумаги MOEX.

**PK:**
`security_id` — внутренний идентификатор записи в БД.

**Внешний идентификатор:**
`tbank_uid` — уникальный идентификатор инструмента T-Invest.

Поле может быть `NULL`, если соответствие с инструментом T-Invest не найдено или T-Invest API временно недоступен.

**Правило сопоставления MOEX и T-Invest:**
Основное сопоставление выполняется по `ISIN`.

Дополнительно проверяется соответствие тикера T-Invest полю `SECID` MOEX и принадлежность инструмента к типу акции.

`tbank_uid` используется только как внешний технический идентификатор и не заменяет `security_id` или `SECID`.

**Правило обновления:**
* новый `SECID` из `config/scope.toml` → добавить запись в справочник;
* существующий `SECID` → актуализировать изменившиеся справочные атрибуты MOEX;
* при успешном сопоставлении с T-Invest → сохранить или актуализировать `tbank_uid`;
* временная недоступность T-Invest не должна препятствовать обновлению основных данных справочника из MOEX;
* при отсутствии нового значения `tbank_uid` уже сохранённый идентификатор не должен затираться `NULL`;
* удаление инструмента из `config/scope.toml` прекращает его дальнейшую загрузку, но не удаляет инструмент и накопленную историю из БД.

**Особенности:**
MOEX остаётся основным источником справочных характеристик акции.

T-Invest используется только для обогащения справочника внешним идентификатором `tbank_uid`.

Отдельная таблица соответствия `security_id ↔ tbank_uid` не создаётся, поскольку в текущей модели используется только один дополнительный внешний идентификатор и его хранение непосредственно в `dwh.security` не усложняет модель.

Текущие торговые показатели и значения предыдущего торгового дня в таблицу не включаются.

Подробный состав колонок и соответствие полям источников фиксируются в `data_dictionary.csv`.

# `index` — справочник индексов

**Назначение:**
Справочник индексов Московской биржи, используемых в проекте.

**Источник:**
MOEX ISS.

Endpoint:
`https://iss.moex.com/iss/statistics/engines/stock/markets/index/analytics`

Используемый блок ответа: `indices`.

**Scope:**
В справочник загружаются индексы, указанные в конфигурации проекта. Текущий набор:

* `IMOEX` — Индекс МосБиржи;
* `MOEXOG` — Нефть и газ;
* `MOEXFN` — Финансы;
* `MOEXIT` — Информационные технологии;
* `MOEXMM` — Металлы и добыча.

Список может расширяться.

**Зерно:**
Одна строка = один индекс.

**Business key:**
`indexid` — код индекса MOEX.

**PK:**
`index_id` — внутренний идентификатор записи в БД.

**Правило обновления:**

* новый индекс добавлен в конфигурацию → получить его данные из MOEX и добавить в справочник;
* существующий индекс → актуализировать справочные атрибуты при их изменении;
* удаление индекса из конфигурации прекращает его дальнейшую загрузку, но не удаляет справочник и накопленную историю из БД.

**Особенность:**
Поля `from` и `till` из источника описывают границы, возвращаемые dataset `analytics`. Их точный смысл не трактуется как дата создания/закрытия индекса без дополнительного подтверждения.

# `calendar` — календарь дат

**Назначение:**
Календарный справочник для единых временных разрезов, группировки данных по периодам и контроля пропущенных дат.

**Источник:**
Генерируется внутри проекта. Внешний API не используется.

**Диапазон:**
Календарь должен покрывать весь период хранения данных проекта и при необходимости автоматически расширяться новыми датами.

**Зерно:**
Одна строка = один календарный день.

**Business key / PK:**
`calendar_date`.

**Правило обновления:**
При необходимости календарь дополняется отсутствующими будущими датами. Уже существующие даты повторно не создаются.

**Особенности:**
Поле `period` хранит идентификатор месяца в формате `YYYYMM` (`202608` = август 2026 года).

# `currency` — справочник валют

**Назначение:**
Справочник валют Банка России, используемых в проекте для хранения и анализа валютных курсов.

**Источник:**
Банк России, официальный XML API.

Endpoint:
`http://www.cbr.ru/scripts/XML_valFull.asp`

Используемый элемент ответа: `Item`.

**Scope:**
Текущий набор валют:

* `R01235` / `USD` — Доллар США;
* `R01375` / `CNY` — Китайский юань.

Список валют может расширяться. При добавлении новой валюты в scope проекта её справочные данные должны быть получены из полного каталога Банка России и добавлены в справочник.

**Зерно:**
Одна строка = одна валюта.

**Business key:**
`cbr_id` — идентификатор валюты Банка России.

**PK:**
`currency_id` — внутренний идентификатор записи в БД.

**Правило обновления:**

* новая валюта добавлена в scope → добавить её в справочник;
* существующая валюта → при необходимости актуализировать её справочные атрибуты;
* исключение валюты из текущего scope прекращает дальнейшую загрузку её курсов, но не удаляет справочник и накопленную историю из БД.

**Особенности:**
Источник содержит полный каталог валют Банка России, однако в БД загружаются только валюты, входящие в scope проекта.

Код валюты `SUR`, используемый в данных MOEX, не следует напрямую связывать с кодами справочника ЦБ без отдельного правила сопоставления.

# `security_daily` — дневные данные по акциям

**Назначение:**
Дневные торговые показатели акций из scope проекта. Используются для расчёта доходности, оборота, ликвидности, волатильности и других дневных метрик.

**Источник:**
MOEX ISS.

Endpoint:
`https://iss.moex.com/iss/history/engines/stock/markets/shares/boards/TQBR/securities/{SECID}.json`

Используемый блок ответа: `history`.

**Scope:**
Загружаются акции, указанные в `config/instruments.py`.

Режим торгов V1 фиксирован: `TQBR`.

**Зерно:**
Одна строка = одна акция за один торговый день.

**Business key источника:**
`SECID + TRADEDATE` в рамках фиксированного режима `TQBR`.

**PK:**
`security_id + trade_date`.

**FK:**

* `security_id` → `security.security_id`;
* `trade_date` → `calendar.calendar_date`.

**Правило загрузки:**
`SECID` из данных MOEX используется для поиска соответствующего `security_id` в справочнике `security`. Сам `SECID` в `security_daily` отдельно не хранится.

Новая комбинация `security_id + trade_date` добавляется в таблицу. При повторной загрузке существующая запись может быть актуализирована, но дубликат не создаётся.

Удаление акции из `config/instruments.py` прекращает её дальнейшую загрузку, но не удаляет накопленную историю.

**Особенности:**
В таблице хранятся основные дневные торговые показатели. Названия акции, `SECID`, режим торгов и другие справочные характеристики здесь не дублируются.

Производные показатели, которые можно получить расчётом из сохранённых данных, отдельно не хранятся.

# `candle_1m` — минутные свечи акций и индексов

**Назначение:**
Хранение минутных свечей акций и индексов из scope проекта. Используется для внутридневного анализа динамики цены, волатильности, объёма и торговой активности.

**Источник:**
MOEX ISS.

Для акций:

`/iss/engines/stock/markets/shares/boards/TQBR/securities/{SECID}/candles.json`

Для индексов:

`/iss/engines/stock/markets/index/boards/{BOARD}/securities/{SECID}/candles.json`

Интервал:

`interval=1`

Используемый блок ответа: `candles`.

**Scope:**
В таблицу загружаются минутные свечи выбранных акций и индексов проекта.

Структура блока `candles` для акций и индексов одинакова, поэтому используется одна общая таблица.

**Зерно:**
Одна строка = одна минутная свеча одной акции или одного индекса.

**PK:**
Отдельный первичный ключ не используется.

**FK:**
- `security_id` → `security.security_id`;
- `index_id` → `index.index_id`.

В каждой строке должен быть заполнен ровно один из двух внешних ключей.

Для свечи акции:
`security_id` заполнен, `index_id = NULL`.

Для свечи индекса:
`security_id = NULL`, `index_id` заполнен.

**Уникальность:**
Уникальность должна гарантироваться по коомбинации:
security_id + index_id + begin

Но лучше дополнительно проработать два случайя.
-Для акций свеча уникальна по комбинации:

`security_id + begin`.

-Для индексов свеча уникальна по комбинации:

`index_id + begin`.

Эти правила должны предотвращать появление дублей при повторной загрузке данных.

**Правило загрузки:**
Блок `candles` не содержит идентификатор инструмента.

При запросе свечей акции `SECID` используется для поиска соответствующего `security.security_id`, который записывается в `security_id`.

При запросе свечей индекса `SECID` используется для поиска соответствующего `index.index_id`, который записывается в `index_id`.

Новые свечи добавляются в таблицу. Повторная загрузка уже существующей свечи не должна создавать новую строку.

Удаление инструмента из scope проекта прекращает дальнейшую загрузку его свечей, но не удаляет накопленную историю.

**Особенности:**
Акции и индексы хранятся совместно, поскольку формат минутных свечей MOEX для них одинаков.

Тип инструмента определяется по заполненному внешнему ключу, поэтому отдельное поле `instrument_type` не требуется.

Отдельный технический идентификатор строки (`candle_id`) не используется, поскольку другие сущности проекта не должны ссылаться на отдельную минутную свечу.

# `dividend` — дивидендные события

**Назначение:**
Хранение истории дивидендных событий по акциям из scope проекта.

Данные используются для последующего расчёта дивидендной доходности, полной доходности акций и других аналитических показателей.

**Источник:**
T-Invest REST API.

Метод:

`InstrumentsService/GetDividends`

Для обращения к API используется `tbank_uid`, сохранённый в `dwh.security`.

**Scope:**
Загружаются дивидендные события только для акций из `dwh.security`, входящих в scope проекта и имеющих заполненный `tbank_uid`.

**Зерно:**
Одна строка = одно дивидендное событие одной акции на дату фиксации реестра.

**Business key / PK:**
`security_id + registry_close_date`.

**FK:**
`security_id` → `security.security_id`.

**Правило загрузки:**
Для каждой акции из `dwh.security` используется сохранённый `tbank_uid`.

По `tbank_uid` через T-Invest API запрашиваются дивидендные события за необходимый диапазон дат.

Основная дата события из источника — `recordDate`, которая преобразуется в `registry_close_date`.

Из ответа используются данные, необходимые текущей модели:

* `security_id`;
* `recordDate` → `registry_close_date`;
* сумма дивиденда → `dividend_value`;
* валюта → `currency_code`.

`tbank_uid`, `SECID` и `ISIN` в таблице `dividend` не хранятся, поскольку идентификационные данные акции находятся в `dwh.security`.

Новая комбинация `security_id + registry_close_date` добавляется в таблицу.

При повторной загрузке существующее событие обновляется через `UPSERT`, что позволяет актуализировать сумму дивиденда и валюту без создания дубликатов.

Удаление акции из scope проекта прекращает дальнейшую загрузку её дивидендных данных, но не удаляет накопленную историю.

**Стратегия обновления:**
Для текущего масштаба проекта допускается повторная загрузка всего диапазона `HISTORY_DATE_FROM – HISTORY_DATE_TO` для каждой акции с последующим `UPSERT`.

Объём дивидендных данных невелик, поэтому полный повторный запрос диапазона предпочтительнее усложнения ETL дополнительной инкрементальной логикой.

При необходимости стратегия может быть пересмотрена после анализа фактического объёма данных и поведения API.

**Особенности:**
Основная дата события — `registry_close_date`, соответствующая `recordDate` T-Invest.

Размер дивиденда хранится вместе с кодом валюты, поскольку валюта относится непосредственно к конкретному дивидендному событию.

Дивиденды могут быть номинированы в разных валютах.

Денежное значение T-Invest, представленное через `units + nano`, должно быть преобразовано в одно точное числовое значение перед загрузкой в DWH.

При недействительном токене T-Invest загрузка дивидендов пропускается, при этом остальные ETL-процессы проекта должны продолжать работать.

# `split` — сплиты и консолидации акций

**Назначение:**
Хранение событий изменения количества акций в результате сплита или консолидации.

**Источник:**
MOEX ISS.

Endpoint:

`/iss/statistics/engines/stock/splits.json`

**Scope:**
В таблицу загружаются события для акций, входящих в scope проекта.

**Зерно:**
Одна строка = одно событие сплита или консолидации одной акции.

**Business key / PK:**
`security_id + trade_date`.

**FK:**
`security_id` → `security.security_id`.

**Правило загрузки:**
`secid` из ответа MOEX используется для определения соответствующего `security_id` в справочнике `security`.

Сам `secid` в таблице отдельно не хранится.

Новая комбинация `security_id + trade_date` добавляется в таблицу. Повторная загрузка существующего события не должна создавать дубликат.

**Особенности:**
Поля `ratio_before` и `ratio_after` описывают соотношение количества акций до и после корпоративного события.

Если `ratio_after > ratio_before` — сплит.

Если `ratio_after < ratio_before` — консолидация.

Отдельное поле типа события не хранится, поскольку тип можно однозначно определить из отношения `ratio_before` и `ratio_after`.

# `index_composition` — состав индексов

**Назначение:**
Хранение истории участия акций в выбранных индексах Московской биржи.

**Источник:**
MOEX ISS. ISS предоставляет отдельные методы аналитики индексов и их тикеров.

Endpoint:

`/iss/statistics/engines/stock/markets/index/analytics/{INDEXID}/tickers.json`

**Scope:**
Загружается информация по выбранным индексам проекта и акциям, присутствующим в справочнике `security`.

**Зерно:**
Одна строка = один период участия одной акции в одном индексе.

**Business key / PK:**
`index_id + security_id + date_from`.

**FK:**
- `index_id` → `index.index_id`;
- `security_id` → `security.security_id`.

**Правило загрузки:**
Индекс определяется из контекста API-запроса.

`SECID` акции из ответа MOEX используется для определения соответствующего `security_id`.

Новый период участия акции в индексе добавляется как новая строка. Повторная загрузка существующего периода не должна создавать дубликат.

Таблица обновляется в рамках ежедневной проверки MOEX-данных. Фактические изменения состава происходят значительно реже; MOEX указывает квартальную ребалансировку фондовых индексов.

**Особенности:**
Таблица хранит именно историю состава индексов, а не ежедневный снимок.

Значение `TILL` пока сохраняется в том виде, в котором его предоставляет MOEX. Его точную трактовку для текущего периода отдельно проверим перед реализацией ETL.

Одна строка = курс одной валюты на одну дату.

**Business key / PK:**
`currency_id + rate_date`.

**FK:**
`currency_id` → `currency.currency_id`.

**Правило загрузки:**
Идентификатор валюты из ответа ЦБ используется для определения соответствующего `currency_id`.

Новая комбинация `currency_id + rate_date` добавляется в таблицу. Повторная загрузка не должна создавать дубликат и при необходимости может актуализировать значение курса.

**Особенности:**
Хранятся как исходное значение курса для указанного номинала (`rate_value`), так и значение курса за одну единицу валюты (`unit_rate`).

Дата хранится как тип `date` и может связываться с `calendar.calendar_date`.

# `key_rate` — ключевая ставка

**Назначение:**
Хранение истории значений ключевой ставки Банка России.

**Источник:**
Банк России.

Метод:

`KeyRateXML`

Используемые поля:

`DT`, `Rate`.

**Зерно:**
Одна строка = одно значение ключевой ставки с даты начала его действия.

**Business key / PK:**
`rate_date`.

**Правило загрузки:**
Новое значение с новой датой добавляется в таблицу.

При повторной загрузке уже существующая дата не должна создавать дубликат и при необходимости может быть актуализирована.

**Особенности:**
В таблице хранится история изменений ставки, а не отдельная запись на каждый календарный день.

Для получения ставки на произвольную дату используется последнее значение, дата которого меньше или равна анализируемой дате.

`rate_date` может связываться с `calendar.calendar_date`.
