# MART Data Model

## 1. Назначение MART

MART — аналитический слой проекта, расположенный между DWH и Apache Superset.

Целевая архитектура:

```text
MOEX / CBR / T-Invest
        ↓
    Python ETL
        ↓
  PostgreSQL DWH
        ↓
  PostgreSQL MART
        ↓
 Apache Superset
```

DWH хранит очищенные исторические факты и справочники.

MART преобразует данные DWH в готовые аналитические наборы:

- рассчитывает производные показатели;
- формирует временные метрики;
- подготавливает данные для BI;
- обеспечивает единое определение аналитических показателей;
- используется как источник для последующих аналитических витрин.

Расчёт MART выполняется преимущественно средствами PostgreSQL.

Python используется для управления обновлением витрин:

- incremental;
- rebuild диапазона;
- full rebuild.

---

# 2. `mart.security_daily_metrics`

## 2.1. Назначение

`mart.security_daily_metrics` — базовая дневная аналитическая витрина по акциям.

Она используется для анализа:

- цены акции;
- изменения цены;
- торговой активности;
- ликвидности;
- исторической волатильности.

В дальнейшем витрина может использоваться как источник для:

- Apache Superset;
- анализа ликвидности;
- сравнения акции с индексами;
- поиска аномалий;
- других MART-витрин.

---

## 2.2. Зерно

```text
1 строка = 1 акция × 1 торговый день
```

Уникальность строки:

```text
security_id + trade_date
```

---

## 2.3. Основные источники

Основной источник:

```text
dwh.security_daily
```

Используемые данные:

```text
security_id
trade_date

open
low
high
waprice
close

value
volume
num_trades
```

Дополнительный источник:

```text
dwh.split
```

Используется для корректировки исторического ценового ряда после:

- дробления акций;
- консолидации акций.

Связь со справочником:

```text
security_id → dwh.security.security_id
```

Наименования и внешние коды акции непосредственно в MART не дублируются.

При необходимости они получаются через `dwh.security`.

# 3. Исходные дневные показатели

В MART сохраняются исходные значения MOEX:

```text
open
low
high
waprice
close

value
volume
num_trades
```

Они не заменяются скорректированными значениями.

Это позволяет одновременно иметь:

```text
raw-показатели MOEX
+
аналитически сопоставимый adjusted-ряд
```

# 4. Корректировка сплитов и консолидаций

## 4.1. Причина корректировки

Проверка исторических данных MOEX ISS показала, что история цен ретроспективно не приводится к единому масштабу после корпоративных событий.

Примеры:

```text
GMKN
08.04.2024
дробление 1 → 100
```

До события цена находилась примерно на уровне:

```text
15 000
```

после события:

```text
150
```

Другой пример:

```text
VTBR
15.07.2024
консолидация 5000 → 1
```

Исторический ценовой ряд также меняет масштаб.

Без дополнительной корректировки такие события создают искусственные:

- ценовые скачки;
- доходности;
- значения волатильности;
- изменения объёма бумаг.

Поэтому аналитические расчёты выполняются на скорректированном ряду.

---

## 4.2. Скорректированные поля

В MART добавляются:

```text
adj_open
adj_low
adj_high
adj_waprice
adj_close
adj_volume
```

---

## 4.3. Коэффициент корректировки цены

Для каждого корпоративного события:

```text
price_factor =
ratio_before / ratio_after
```

Исторические цены до события корректируются:

```text
adjusted_price =
raw_price × price_factor
```

Пример дробления:

```text
1 → 100

price_factor = 1 / 100
```

Историческая цена:

```text
15 000
```

становится:

```text
150
```

Пример консолидации:

```text
5000 → 1

price_factor = 5000 / 1
```

Историческая цена:

```text
0.02
```

становится примерно:

```text
100
```

---

## 4.4. Корректировка объёма

Количество бумаг изменяется обратно цене.

Для объёма:

```text
volume_factor =
ratio_after / ratio_before
```

и:

```text
adj_volume =
volume × volume_factor
```

Пример:

```text
дробление 1 → 100
```

Цена:

```text
÷ 100
```

Количество бумаг:

```text
× 100
```

---

## 4.5. Показатели, которые не корректируются

Не корректируются:

```text
value
num_trades
```

`value` представляет денежный оборот и уже выражает стоимость совершённых торгов.

`num_trades` отражает фактическое количество сделок. Корпоративное событие не изменяет количество исторически совершённых сделок.

---

## 4.6. Несколько корпоративных событий

Если у акции произошло несколько последовательных сплитов или консолидаций, используется накопленный коэффициент всех последующих событий.

Пример:

```text
Дата A
   ↓
Split 1
   ↓
Split 2
   ↓
текущая дата
```

Для данных до `Split 1` применяются коэффициенты:

```text
Split 1 × Split 2
```

Для данных между событиями:

```text
только Split 2
```

Для данных после последнего события:

```text
коэффициент = 1
```

Таким образом вся историческая серия приводится к масштабу, действующему после последнего известного корпоративного события.

---

# 5. Временные интервалы

Основные аналитические горизонты:

```text
1D
1W
1M
3M
```

Используются календарные границы периода.

Для строки с датой `D`:

```text
1D = текущий торговый день

1W = D - 1 календарная неделя → D

1M = D - 1 календарный месяц → D

3M = D - 3 календарных месяца → D
```

В расчётах используются только реально существующие торговые наблюдения внутри выбранного диапазона.

Если в начале периода отсутствуют торговые данные, используется первая существующая торговая строка внутри периода.

Например:

```text
календарный период:
01.01–31.01

первая доступная торговая строка:
10.01
```

Расчёт выполняется по:

```text
10.01–31.01
```

Период не считается отсутствующим только из-за отсутствия наблюдений в его начале.

---

# 6. Изменение цены

Рассчитываются:

```text
price_change_1d
price_change_1w
price_change_1m
price_change_3m
```

Все показатели рассчитываются по скорректированным ценам.

---

## 6.1. `price_change_1d`

Изменение цены внутри текущей торговой сессии:

```text
price_change_1d =
adj_close / adj_open - 1
```

---

## 6.2. `price_change_1w`

Определяется первая существующая торговая строка внутри календарного недельного окна.

Расчёт:

```text
adj_close текущей даты
--------------------------- - 1
adj_open начала периода
```

---

## 6.3. `price_change_1m`

Аналогично:

```text
adj_close текущей даты
--------------------------- - 1
adj_open начала периода
```

для календарного окна в один месяц.

---

## 6.4. `price_change_3m`

Аналогично для календарного окна в три месяца.

---

# 7. Ликвидность

Используются три базовых показателя:

```text
value
volume
num_trades
```

Для каждого рассчитывается среднее дневное значение за:

```text
1W
1M
3M
```

---

## 7.1. Денежный оборот

Поля:

```text
avg_value_1w
avg_value_1m
avg_value_3m
```

Расчёт:

```text
AVG(value)
```

по торговым строкам внутри соответствующего календарного периода.

`value` не требует корректировки на сплит.

---

## 7.2. Объём бумаг

Поля:

```text
avg_volume_1w
avg_volume_1m
avg_volume_3m
```

Расчёт:

```text
AVG(adj_volume)
```

Используется скорректированный объём, чтобы дробления и консолидации не создавали искусственных изменений количества обращавшихся бумаг.

---

## 7.3. Количество сделок

Поля:

```text
avg_num_trades_1w
avg_num_trades_1m
avg_num_trades_3m
```

Расчёт:

```text
ROUND(AVG(num_trades))
```

Результат хранится как:

```text
BIGINT
```

Дробная часть среднего количества сделок аналитически не используется.

---

# 8. Волатильность

Рассчитываются:

```text
volatility_1w
volatility_1m
volatility_3m
```

`volatility_1d` в дневной витрине не рассчитывается.

Для внутридневной волатильности в дальнейшем используются данные:

```text
dwh.candle_1m
```

---

## 8.1. Дневные изменения

Внутри каждого периода строится последовательность изменений скорректированной цены закрытия:

```text
return_t =
adj_close_t / adj_close_(t-1) - 1
```

Обе торговые даты должны находиться внутри анализируемого временного диапазона.

Цена предыдущей торговой сессии за пределами периода не используется.

---

## 8.2. Расчёт волатильности

Волатильность определяется как стандартное отклонение дневных изменений цены:

```text
STDDEV(daily_return)
```

Расчёт выполняется отдельно для:

```text
1W
1M
3M
```

Результат хранится как доля.

Например:

```text
0.012
```

соответствует:

```text
1.2%
```

Annualized volatility в текущей версии не рассчитывается.

---

# 9. NULL

Исходные значения `NULL` не заменяются нулями.

Если для вычисления метрики отсутствует обязательное значение:

```text
результат = NULL
```

Например:

```text
open = NULL
```

означает:

```text
price_change_1d = NULL
```

Для агрегатов PostgreSQL используется стандартная логика:

```text
AVG()
STDDEV()
```

отдельные `NULL` наблюдения игнорируются.

Если наблюдений недостаточно для вычисления статистической величины, результат остаётся `NULL`.

# 10. Обновление MART

`security_daily_metrics` является физической таблицей.

Поддерживаются три режима обновления.

---

## 10.1. Incremental

Основной рабочий режим.

После загрузки новых данных в DWH определяются ключи:

```text
security_id + trade_date
```

которые ещё отсутствуют в MART.

Для них рассчитываются новые строки.

Для расчёта исторических метрик SQL может читать предыдущую историю DWH, однако в MART записываются только новые результаты.

---

## 10.2. Rebuild range

Используется при исправлении или догрузке исторических данных.

Пример:

```text
обнаружен отсутствующий день:
17.05.2023
```

После исправления DWH необходимо пересчитать:

```text
17.05.2023
→
примерно 17.08.2023
```

поскольку максимальное аналитическое окно составляет три календарных месяца.

При расчёте строк в начале диапазона SQL дополнительно читает необходимую предшествующую историю.

---

## 10.3. Изменения `dwh.split`

Добавление или исправление корпоративного события может изменить весь исторический adjusted-ряд до даты события.

Поэтому изменение данных `dwh.split` требует пересчёта всех затронутых исторических строк соответствующей акции.

Если изменение существенно влияет на большую часть истории, допускается полный rebuild витрины.

---

## 10.4. Full rebuild

Полная пересборка используется при:

- изменении формул;
- изменении структуры MART;
- изменении логики split-adjustment;
- массовом исправлении исторических данных;
- необходимости полной проверки воспроизводимости.

Принцип:

```text
DWH = источник истины

MART = полностью воспроизводимый производный слой
```

---

# 11. Ключи и связи

Первичный ключ:

```text
PRIMARY KEY (
    security_id,
    trade_date
)
```

Внешний ключ:

```text
security_id
→
dwh.security(security_id)
```

Отдельный искусственный `mart_id` не используется.

---

# 12. Индексы

Первичный ключ:

```text
security_id + trade_date
```

обслуживает запросы истории одной акции.

Дополнительно предусматривается индекс:

```text
trade_date
```

для выборок всех инструментов на определённую дату или диапазон дат.

Дополнительные индексы на аналитические показатели заранее не создаются.

Они добавляются только при подтверждённой необходимости после анализа реальных запросов через:

```text
EXPLAIN ANALYZE
```

# 14. Что не входит в `security_daily_metrics`

В текущую витрину сознательно не входят:

```text
дивиденды
total return
реинвестирование дивидендов
просадки
maximum drawdown
liquidity ranking
сравнение с индексами
аномалии
внутридневная волатильность
агрегированные минутные свечи
календарные месячные/квартальные агрегаты
```

Эти задачи относятся к другим аналитическим наборам или последующим MART-витринам.

---

# 15. Временная аналитика более высокого уровня

Отдельно предполагается анализ календарных периодов:

```text
неделя
месяц
квартал
```

Для таких периодов могут рассчитываться:

```text
open_period
high_period
low_period
close_period
avg_price_period

value_period
volume_period
num_trades_period
```

Например, сравнение:

```text
January 2020
vs
January 2026
```

может выполняться по средней стоимости акции соответствующего календарного месяца.

Эта аналитика не включается непосредственно в `security_daily_metrics` и будет проектироваться отдельно.

---

# 16. Внутридневная аналитика

Для внутридневных расчётов используется:

```text
dwh.candle_1m
```

Из минутных свечей впоследствии могут формироваться полные фиксированные интервалы:

```text
15m
30m
1h
```

Дашборд работает только с завершёнными временными периодами.

Незавершённый текущий торговый день и незакрытые внутридневные интервалы в аналитические показатели не включаются.
