# ETL Design — MOEX Analytics Platform

## 1. Назначение ETL

ETL-слой загружает данные из MOEX ISS, Банка России и T-Invest, приводит их к структуре DWH и записывает в PostgreSQL.

Целевой поток:

```text
MOEX / CBR / T-Invest
        ↓
      Python
        ↓
   PostgreSQL DWH
```

Отдельный постоянный RAW/SOURCE-слой не используется: исходные ответы API существуют только во время выполнения ETL.

---

## 2. Разделение ответственности

- `api/` — HTTP-запросы к внешним источникам и базовая проверка ответов.
- `etl/` — расчёт диапазонов загрузки, преобразование данных и подготовка строк для DWH.
- `db/read.py` — чтение служебных данных из DWH: ID, уже загруженные диапазоны и т. п.
- `db/write.py` — параметризованные `INSERT ... ON CONFLICT DO UPDATE`.
- `etl/common.py` — только действительно общие ETL-helper'ы.
- `pipeline.py` — порядок запуска всех ETL-процессов.
- `settings.py` — единая точка получения настроек проекта и переменных окружения.

ETL-модули не должны самостоятельно открывать соединения с БД и не должны содержать HTTP-логику источников.

---

## 3. Scope и даты

Scope инструментов и общий аналитический период задаются конфигурацией проекта.

Для обычного рабочего запуска конечная дата может задаваться динамически как «вчера» в `settings.py`. Это позволяет не загружать незавершённый текущий день.

Фиксированная дата окончания всё равно должна оставаться доступной для воспроизводимых тестовых и исследовательских запусков.

---

## 4. Инкрементальная загрузка дневных данных

Для `security_daily`, `index_daily` и `currency_rate` используется единая логика расчёта недостающих крайних диапазонов:

1. Определяется целевой диапазон.
2. Из DWH читаются `MIN(date)` и `MAX(date)`.
3. Если данных нет — загружается весь целевой период.
4. Если диапазон полностью покрыт — загрузка не выполняется.
5. Если не хватает данных слева и/или справа — загружаются только отсутствующие края.

Общий helper:

```python
calculate_missing_date_ranges(
    target_from,
    target_to,
    loaded_from,
    loaded_to,
)
```

Внутренние пропуски между `MIN` и `MAX` в V1 специально не ищутся.

---

## 5. Особенность минутных свечей

`candle_1m` использует отдельную логику диапазонов.

Причина: одна календарная дата содержит множество минутных строк. Наличие `MAX(begin_ts)::date` ещё не гарантирует, что крайний день был загружен полностью.

Поэтому при расширении диапазона крайняя уже загруженная дата включается повторно:

```text
обычные дневные данные:
БД 10–20 → нужен период 5–25
загрузка: 5–9 и 21–25

минутные свечи:
БД 10–20 → нужен период 5–25
загрузка: 5–10 и 20–25
```

Повторная загрузка безопасна благодаря UPSERT.

Свечи дополнительно разбиваются на чанки по 30 дней, чтобы не выполнять слишком большие запросы и записи за один проход.

---

## 6. Пагинация

Пагинация MOEX остаётся в конкретных ETL, где она нужна.

Для дневной истории используется `history.cursor`.

Для минутных свечей страницы запрашиваются до тех пор, пока API не вернёт пустой набор строк.

Общий универсальный pagination-helper пока не вводится: механизмов немного, а их поведение различается.

---

## 7. Преобразование данных

Основные правила:

- даты приводятся к Python `date`;
- timestamp свечей — к `datetime`;
- nullable integer-поля pandas — к `Int64`;
- пропуски pandas/NumPy перед записью заменяются на `None`, чтобы PostgreSQL получил `NULL`;
- денежные и точные десятичные значения, хранящиеся в PostgreSQL как `NUMERIC`, по возможности передаются через `Decimal`, а не через `float`;
- названия колонок источника приводятся к модели DWH внутри `transform_*`.

Общее преобразование DataFrame в параметры SQL вынесено в:

```python
dataframe_to_rows(df)
```

---

## 8. Запись в PostgreSQL

Все записи выполняются через `db/write.py`.

Публичные функции имеют прикладной смысл:

```python
upsert_security_daily(...)
upsert_index_daily(...)
upsert_dividend(...)
...
```

Повторяющийся технический механизм записи вынесен во внутренний helper.

Запись выполняется через `cursor.executemany(...)` и параметризованный SQL.

Для основных таблиц используется `INSERT ... ON CONFLICT DO UPDATE`, поэтому повторный запуск ETL не должен создавать дубликаты.

Контекстный менеджер соединения psycopg сохраняет текущую транзакционную семантику: успешный блок фиксируется, исключение приводит к rollback и пробрасывается выше.

---

## 9. T-Invest

T-Invest используется как дополнительный источник:

- для `tbank_uid`;
- для дивидендных событий.

Токен проверяется один раз в начале pipeline.

Если токен невалиден или неактивен:

- основная MOEX/CBR-часть pipeline продолжает работать;
- загрузка T-Invest-зависимых данных пропускается;
- ранее сохранённый `tbank_uid` не должен затираться `NULL`.

При чтении UID из DWH выбираются только строки, где `tbank_uid IS NOT NULL`.

---

## 10. Оркестрация

`pipeline.py` является верхнеуровневой точкой запуска ETL.

Сначала загружаются справочники, затем факты и исторические данные, затем связанные сущности и события.

Принцип порядка:

```text
справочники
    ↓
факты / история
    ↓
события и связи
```

Примеры зависимостей:

```text
security → security_daily / split / dividend / index_composition
index    → index_daily / candle_1m / index_composition
currency → currency_rate
```

Неожиданная ошибка ETL должна останавливать pipeline. Исключение — заранее предусмотренный сценарий недоступности T-Invest.

---

## 11. Логирование

Основной принцип:

- `INFO` — итог ETL, отсутствие новых данных, крупный прогресс длительных операций;
- `DEBUG` — диапазоны, параметры API, пагинация и технические детали;
- `WARNING` — ожидаемая деградация, например недоступный T-Invest;
- `logger.exception()` — необработанные ошибки.

Для `candle_1m` допустим промежуточный `INFO` по инструменту, потому что этот ETL выполняется заметно дольше остальных. Детализация по чанкам и страницам остаётся на `DEBUG`.

---

## 12. Идемпотентность и ограничения V1

ETL проектируется так, чтобы повторный запуск:

- не создавал дубликаты;
- не перезагружал полностью уже покрытые дневные периоды;
- корректно повторно загружал граничную дату свечей;
- безопасно обновлял изменившиеся значения через UPSERT.

Сознательные ограничения V1:

- внутренние пропуски между `MIN` и `MAX` автоматически не ищутся;
- отдельный RAW/SOURCE-слой не хранится;
- сложный DAG/оркестратор на уровне Python не вводится;
- пагинация пока не унифицируется между разными API-механизмами.

Эти ограничения допустимы для текущего масштаба проекта и могут быть пересмотрены при переходе к Prefect и более зрелому контролю качества данных.
